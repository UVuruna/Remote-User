## What This Project Is

Remote control of the Windows PC from an Android tablet/phone over LAN. The PC runs a Python server (screen capture + input injection); the tablet runs **no native app** — it opens a web page served by the PC. Full architecture and design decisions: [Remote User](README.md). Phase status: [Roadmap](ROADMAP.md).

## Tech Stack (decided — do not relitigate without owner approval)

**The authoritative record of the product direction and build plan is [ROADMAP.md](ROADMAP.md#direction) (Product Direction, decided 2026-07-22). Read it before proposing architecture changes.** Summary:

- **Server:** Python 3.13, FastAPI + uvicorn, `dxcam` (DXGI capture), `ctypes` → Win32 `SendInput` (injection), `qrcode` (pairing). Two entry points around one `server_core`: `gui_main.py` (PySide6 window + tray — what the packaged EXE runs) and `main.py` (headless CLI). `bootstrap.init_process()` (DPI → logging → user settings) MUST run before any screen-touching import.
- **Streaming:** **H.264** via ffmpeg, hardware-encoded with auto-detection (NVENC → QuickSync → AMF) and a **libx264 software fallback** so it runs on any PC; output is fragmented MP4 decoded by the client via MSE, at **native monitor resolution** by default (`h264_max_width`). JPEG-per-frame is the fallback when no ffmpeg/encoder exists. (Measured ~3.6 Mbps static native 4K vs ~37 Mbps JPEG at quarter resolution.) Bundled ffmpeg is **pinned to 7.1.1** — newer builds require NVENC API 13.1 (driver ≥ 610) and silently drop to software encoding on older drivers.
- **Product = two installable apps:** a Windows desktop app (server + GUI + tray, `.exe`) and an Android **hybrid** app (native Kotlin shell in `android/` + WebView reusing the web client, shipped as an APK; the shell adds only what a browser cannot — pairing, real-app link routing, file chooser, `Android.rescan()` / `Android.setTailscaleUrl()` bridge — ALL guidance lives once, in the page). The shell stores **two addresses** (LAN from pairing + Tailscale learned from every `config` via the bridge) and probes `/ping` on both at start, loading whichever answers — the app connects at home AND on mobile data with no user choice (a single stored URL was the live failure: LAN address on mobile data = minutes of `ERR_CONNECTION_TIMED_OUT`). The probe counts ONLY the exact 204 as alive (captive portals on foreign Wi-Fi answer anything with a 2xx/redirect login page — live failure 2026-07-27; the 204 contract is pinned in the build gate), the error card keeps re-probing by itself (4 s timer + instant re-probe on every default-network change) because a one-shot "Try again" always fired mid-flap on flaky foreign Wi-Fi, that card names the CAUSE instead of one generic message (owner 2026-08-04 — no network / PC not on Tailscale / Tailscale missing / Tailscale off / PC down, read from network capabilities + package visibility, with the primary button being the fix: Install Tailscale, Turn Tailscale on — the shell opens the app since Android cannot flip another app's VPN switch — or Try again), and a session running over an unfamiliar Wi-Fi (LAN dead, tunnel alive, Wi-Fi transport) gets a one-per-stay security toast. **NO browser EVER shows the client — on ANY device** (owner rule 2026-07-22, shouted; hardened 2026-08-02 after the live tablet failure: Chrome on Android tablets sends a desktop-Linux User-Agent with no `Android` token, so "detect Android" routing served the tablet the live client): the server serves the client ONLY to the APK's WebView (it appends a `RemoteUserApp` User-Agent marker) and routes every other User-Agent to `client/install.html` — a full-screen funnel whose FIRST, primary button is **Open the app** (`intent://pair?url=…` hands the tokened URL to the app; it pairs itself — nothing typed, nothing scanned; a camera-scanned QR always lands in the browser first, an Android platform limit for plain-http links, so every post-install scan must be exactly one tap), with the one-time Install (`/app.apk`) below it. After install the QR is not part of daily use — the user just opens the app; re-pairing happens IN the app. Desktop browsers get the funnel too (dev exception: only a checkout with no APK built serves the client — an official install always bundles the APK). The desktop installer bundles the APK.
- **Connection:** a mesh VPN installed on both devices (Tailscale recommended), one-time, wizard-guided; works anywhere incl. mobile data via the mesh's free relay. Server already binds all interfaces + pairing detects the Tailscale address, so this is code-ready.
- **Login = the Tailscale login** (owner decision, option a): the mesh identity IS the account; one login per device, no custom account backend.
- **The app installs/drives all dependencies — the user never side-installs anything** (hard owner requirement). Wizard in the `.exe` AND the APK: ffmpeg bundled; Tailscale chain-installed on desktop / store-deep-linked-and-detected on Android; user only follows in-app prompts. Never tell the *end user* to download/copy/configure anything (telling the *owner* to install a dep for dev-time testing is fine, but say so explicitly).
- **Client UI:** vanilla HTML/CSS/JS in the WebView, Pointer Events, canvas rendering — no framework, no build step.
- **Hard constraints (owner):** no payment for any required part; third-party services/installs OK if best; not over-indexing on privacy/security. Don't fight mature remote-desktop tools on latency — the unique value is the **app-aware companion layer** (Windows UI Automation state reading, notifications, per-app controls).
- **Open decisions** (see ROADMAP): mesh provider (Tailscale vs ZeroTier), distribution (APK vs later Play Store), build order.

## Architecture Constraints

1. **One monitor per view.** The client always displays and controls exactly one monitor; a switch button changes which. Client coordinates are ALWAYS normalized 0–1 within the displayed monitor; the server maps them to that monitor's rect. Never send virtual-desktop-wide coordinates.
2. **The server process must declare DPI awareness** (`DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2`) before any capture or injection — otherwise Windows silently rescales injected coordinates.
3. **No input before auth.** The WebSocket handler rejects every message until a valid token arrives. This is a hard security rule (Remote Mouse CVE class), not a nice-to-have.
4. **Unicode text goes through `KEYEVENTF_UNICODE`** (VK_PACKET), never through virtual-key mapping. Special keys (Enter, Backspace, arrows, Tab, Esc) go through VK codes. Two distinct protocol messages: `key_text` vs `key_special`.
5. **Client keyboard capture:** an invisible but REAL-SIZE focusable `<textarea>` — full-width, ~42px tall, at the top, rendered fully transparent (transparent text/caret/background) with `pointer-events:none`, font ≥16px. NOT `display:none`, NOT `opacity:0`, and NOT 1px×1px: a 1px field made Android IMEs silently refuse to raise the keyboard / attach voice input (found live 2026-07-22 — typing and dictation both dead). A textarea so the phone IME shows ↵/new-row instead of a Send/Go key; `autocapitalize/autocorrect/autocomplete/spellcheck` disabled; printable characters via input-event diffing (the diff replays surviving-suffix edits too), structural keys via `keydown`. Never trust `keydown.key` for printable characters (Android IME).
6. **The finger steers, buttons act — and NOTHING is a tap** (owner decision 2026-07-22, hardened 2026-07-26): the one-finger gesture ONLY moves the PC cursor — it never clicks. Left AND right clicks are explicit press buttons (`click {button}` — down+up at the current cursor position; twice fast = double click); the old right-click-on-tap mode is GONE — with the offset pointer a tap would land away from the fingertip, so no canvas tap may ever act. Toggle modes (drag/scroll) stay; two fingers = local pinch zoom/pan, never clicks. No timed gestures, ever. **The pointer sits EXACTLY under the finger** (owner decision 2026-08-02, reversing the 2026-07-26 offset system after living with it on-device): no handedness diagonal, no calibration, no reserved edge margins — the image aspect-fits the FULL canvas and a focused layout touches all four screen edges. `config.hand` is still sent but the client ignores it.
7. **Ghost-pointer self-healing** (live bug 2026-07-22): Android WebView occasionally loses a `pointerup`/`pointercancel`; a stale entry in the pointer map made EVERY later tap register as a pinch until page refresh ("input randomly stops working"). On every `pointerdown` with `isPrimary`, the client wipes pointer/pinch/primary state — a new primary pointer is the browser's guarantee no other finger is really down. Do not remove this reset.
8. **Session lives only while the owner is looking** (owner security decision): the client closes the WebSocket when the page is hidden (tab backgrounded / screen locked) and reconnects **immediately** on return (`visibilitychange` → connect, not just the 2 s retry interval — the wait swallowed the first taps after every app switch). A `send()` on a dead socket must stay VISIBLE (status pill "Reconnecting…") — silently dropping it read as "buttons randomly stopped working" over a frozen frame. **UIPI is the proven total-input killer and is now DEFENDED twice** (live failure 2026-07-29, the recurring "every release breaks the mouse" ghost): Windows silently discards ALL `SendInput` from a non-elevated process — the call still returns success — whenever an ELEVATED window has focus (the owner's admin VSCode after every dev session; stream fine, zero errors, dead mouse; confirmed by controlled A/B on the installed app — medium = zero movement, elevated = pixel-exact). Defense: (1) the packaged app runs **elevated always** (`--uac-admin`; autostart via Task Scheduler `/RL HIGHEST` because HKCU Run silently skips elevated apps); (2) the injector **verifies its own moves** (`InjectionMonitor`: commanded jump ≥ threshold must land; a miss streak → server ERROR log + client toast) — if anything ever eats input again (lock screen, future policies), the phone SAYS so instead of gliding a local cursor over a dead session. The monitor's logic is pinned in the build gate; never remove either defense.
9. **Control buttons fire on pointerup PLUS a pointercancel rescue, and the input pipeline is gated** (live failure 2026-07-26 — every button dead on the real device, only the keyboard toggle alive): Android ends touches that start near screen edges / system-gesture zones with a `pointercancel`, so an up-only tap handler simply never runs — and with `targetSdk 35` the WebView is drawn edge-to-edge, so the nav bar also sat ON TOP of the bottom controls (the shell now hides the system bars — immersive, swipe reveals them transiently). `keepFocus` therefore fires on pointerup (touch grants transient user activation at UP — the file picker and IME focus need it; plain down-firing broke them) AND on a pointercancel whose travel stayed under `CANCEL_TAP_SLOP` — a stolen tap still acts, while a system home/back swipe crossing a button (real travel, then cancel) never does. Never simplify this back to bare `click`/pointerup, and never remove `tests/test_input_pipeline.py` from `build.py` (the fail-closed INPUT GATE that proves touch → protocol → injection end-to-end before anything ships; its layout comes from `tests/fixtures/actions.json`, pinned so owner edits to the real actions.json can't block builds).

## Protocol

- Client → server (JSON text): `auth {token, screen {w, h}}` (`screen` = the device's size; its aspect drives layout window sizing — tablet vs phone), `pointer_down/pointer_up {x, y, button}`, `click {button}` (down+up at the CURRENT cursor position, no coordinates), `press {button, down}` (owner 2026-08-04 — the CLICK/HOLD mouse buttons Click/Right/Middle: DOWN when the finger lands on the button, UP when it lifts, at the current cursor — a tap is a click, a held finger holds the PC button like a real mouse; `button` is `"left"`/`"right"`/`"middle"`/`"x1"`/`"x2"` — the last two are the SIDE buttons Btn 4 / Btn 5, owner 2026-08-05, reserves in the Mouse pool), `pointer_move {x, y}`, `scroll {x, y, ticks}`, `viewport {x, y, w, h}` (JPEG mode only — H.264 always streams the full frame), `key_text {text}`, `key_special {key}`, `chord {chord}`, `monitor_switch {}`, `screenshot {x?, y?, w?, h?, paste?}` (the Attach set's Shot sends the REGION the phone currently views — zoom / layout focus, never the whole desktop — plus `paste:true`, and the server crops, fills the clipboard and injects Ctrl+V itself; the legacy snap sends neither), `client_log {text}` (silent phone-side diagnostics — voice evidence — written to the server log, owner 2026-08-05), and the layout messages (Phase F+ step 1): `layout_pick {x, y}` (one armed tap — a grid takes one tap per cell), `layout_list {}` (the list creation source: the server enumerates every window AND its content tabs), `layout_create {slots, mode, grid, orient, name?}` (`slots` = ordered cells `{hwnd, tab|null, x, y}`; `name` is the owner's own name for the layout — owner 2026-08-05, the creation panel prefills the target window's title and an empty string keeps it; every tab slot is EXTRACTED into its own window first — app's own menu command → Explorer path → SendInput drag; every failure falls back to that slot's whole window), `layout_focus {index}` (−1 = full desktop, which also MINIMIZES every layout member so the desktop shows only non-layout windows), `layout_remove {index}`, `layout_rename {index, name}` (owner 2026-08-05 — renaming an existing layout from the list's pencil; nothing on the PC moves), `layout_aspect {index, w, h, pos?}` (owner 2026-08-03 — that layout's own W:H, `0/0` = back to the phone's own shape; the region may only ever be made SMALLER than the phone's shape: portrait keeps the full width and loses height, landscape keeps the height and loses width; `pos` 0–1000 — owner 2026-08-05, the resize panel's center Move handle (a DRAWN four-way arrow — `ICONS.move`, never a font glyph: the ✥ character came out a blunt cross on the owner's phone, owner 2026-08-05 — drag along the free axis, double-tap re-centers) — places the shrunken region instead of always centering it, 500 = centered), `next_input {}` (UIA-cycled focus through TEXT-INPUT fields — full desktop → all visible windows, layout focus → that layout's members only; built for dictation), and `quality {fps, res, bitrate}` (owner 2026-08-05, replacing the full/reduced cycler: the Quality button opens a PANEL — FPS Max/10/15/30/60, resolution full/⅔/½ (half PER AXIS is quarter pixels, so the middle step is ⅔ — owner), bitrate high/mid/low as percentages of the desktop bitrate — the phone can never out-bid the PC's ceiling on any of the three axes, and the panel SAYS so (PC's live values in the header, unreachable fps steps struck through) — plus a "save data on mobile networks" checkbox; the client sends the EFFECTIVE values — auto-on-cellular applies the saving profile via the shell's `Android.transport()` bridge — per client via its own ffmpeg, restated on every connect; legacy `quality {reduced}` still maps to the saving profile). **Presence** (owner 2026-08-05): `hb {}` every 4 s while the page is visible, and `away {excursion}` as the parting word when the page hides. Layout members are always-on-top while the phone shows them, so the server MUST learn the moment the phone stops working — and a locked phone rarely manages a clean socket close (its Wi-Fi sleeps, the connection just goes quiet; the live symptom was the owner sitting down at his PC under hovering layout windows). Silence of 12 s, or an `away` that is not an excursion, ENDS the session: every layout member leaves the topmost band and is minimized, exactly like choosing Desktop. An EXCURSION (image picker, camera, voice, permission dialog) is the owner still working with us — the layout stands, with a 5-minute backstop. The layout last used is remembered SERVER-side and the next connection RESUMES there, never on the desktop (only a deliberate Desktop choice makes the desktop the resume state). Coordinates are always 0–1 within the displayed monitor. **One device at a time** (owner 2026-08-02): a new authenticated socket closes the previous one with code **4409**, and that client must NOT auto-reconnect (deliberate tap only) — two devices would otherwise steal the session in a loop.
- Server → client (JSON text): `config {monitor_width, monitor_height, stream, codec?, hand, tailscale_url, app_version, base}` — `base` (owner 2026-08-05) is the DESKTOP Settings card as the phone must read it (`{fps, width, height, bitrate, bitrate_mid, bitrate_low}`): the desktop sets the base and the phone's quality panel may only go BELOW it, so the panel states the PC's live values and strikes out every step that cannot take effect. Without it the phone showed "30 fps" lit under a 10 fps PC and the bitrate steps were absolute constants that discarded the PC's own choice the moment the phone left "High" — which read as "the desktop settings do nothing"; `h264_bitrate_mid_pct`/`_low_pct` make Mid/Low percentages of the desktop bitrate — `hand` (`"right"`/`"left"`, desktop Settings) is legacy — ignored by the client since the offset system was dropped (2026-08-02) — after auth and after EVERY stream (re)start (monitor switch, H.264 session reset); the client must fully reset its view and decode pipeline. `stream` is `"h264"` or `"jpeg"`; `codec` (H.264 only) is the exact MSE string (e.g. `avc1.4D4028`) parsed server-side from the live init segment's `avcC` box — never guessed; `tailscale_url` is the works-anywhere address with token (null until the PC is signed in to Tailscale) and feeds the client's guided wizard; `app_version` is the server's version — inside the APK the page compares it with the shell (`Android.appVersion()`) and offers the in-app update banner. `actions {sets}` (radial-wheel shortcut sets from `actions.json`, after auth), `toast {text}` (user-facing notice shown on the status pill), `cursor {x, y}` (PC pointer position, normalized, sent on change ~30 Hz — DXGI capture never contains the pointer; the client draws a virtual cursor in both modes), `layout_state {layouts, active, region, orient}` (after auth and on every layout change — the registry lives server-side for the server's lifetime; `region` is the monitor-normalized rect the client locks its view onto) and `layout_offer` (two shapes: the answer to `layout_pick` — `{target, tab, x, y, grids}`, one tapped slot; and the answer to `layout_list` — `{entries, grids}`, every window plus each window's content tabs as separate entries; entries carry real app icons as PNG data URIs). Each entry in `layout_state.layouts` also carries its `ratio` (`[w, h]` or null) and `pos` (0–1 free-axis position of the shrunken region, 0.5 = centered — owner 2026-08-05). The creation list **leaves out windows that already belong to a layout** (one window cannot be shown twice) and offers tabs **only from tab-capable apps** (`uia.TAB_APPS` — an app's internal section switcher is a UIA `TabItem` exactly like a Chrome tab, and extracting it always failed back to the whole window). Creation UI: the Layout (+) button opens a source chooser — "From a list" or "Tap a window" — both feed the same slot-based panel; a loading overlay covers the visible seconds of server-side tab extraction. **The loading animation lasts as long as the work does** (owner 2026-08-03, repeatedly): `layout_state` only arms a settle watcher that samples the live frame, and the overlay drops when the streamed screen actually stops moving — the user never watches windows climb out of the taskbar. It cross-fades in/out and opens on the next cube face every time (top → left → back → right → front → bottom; face colours in `style.css`). **Layout focus survives excursions** (owner 2026-08-04): server-side focus is per-connection, and every excursion that hides the page (gallery pick, permission dialog) closes the socket by rule — the client therefore remembers the focused layout (`layoutRestore`) and, when a fresh connection's first `layout_state` says desktop without the user having chosen it, re-sends `layout_focus` once (same index AND name, else skipped); a deliberate desktop/remove choice clears the memory and is never overridden. **`layout_state` is a VERIFIED claim** (owner 2026-08-04, after "stopped moving" lied twice): the server holds it until every member's frame rect actually matches its commanded rect (`wait_landed` — position, not stillness; a refusal reaches the phone as a toast, never a silent warning). **Layout members are TOPMOST from first touch until the layout stops being shown** (owner decree 2026-08-04: never below ANY other window, incl. always-on-top ones, during creation or focus); `drop_topmost` strips it on desktop focus, focus of another layout, removal, and disconnect — nothing stays always-on-top for the owner at the desk.
- **Everything is guided IN the apps — never in chat/manuals** (hard owner principle, restated angrily 2026-07-22 and binding): any step a user must perform gets step-by-step on-screen guidance with plain language and automatic continuation. Desktop: three-state Tailscale card (install / sign in / connected). Phone first contact: the **QR always encodes the LAN address**, and the FIRST scan hard-requires the phone on the home Wi-Fi (a fresh phone has no tunnel to the PC — with mobile data the LAN address loads NOTHING, just a dead dark page; hit live 2026-07-22). The PC window states this requirement under the QR — the only place that can, since an unreachable page cannot guide anyone. Opening the QR in the phone browser lands on the **install funnel** (Open the app first/primary; Install below → paired automatically via `intent://` — the browser never shows anything else). Inside the app, the client page shows an "anywhere access" banner (auto-appears ONCE per device — owner 2026-07-26; afterwards Settings → Anywhere reopens it) → in-page wizard: Google Play deep link for the Tailscale app → sign-in step → the page polls `GET /ping` (auth-free 204, reachability only) on the Tailscale address and hands over the permanent works-anywhere link the moment the phone joins. Never send the end user outside the guided flow.
- Server → client (binary), by announced mode: **H.264** — the raw fragmented-MP4 byte stream (init segment first; the client appends chunks into MSE in arrival order). **JPEG** — 16-byte header (4 × float32 LE — monitor-normalized x, y, w, h of the region the frame covers) + JPEG bytes.
- **H.264 streaming is per-client**: one shared capture feeds one ffmpeg process per connected client (fresh init segment + keyframe at connect — no mid-stream joining). H.264 bytes are never dropped individually; a client that falls a full queue behind gets its whole session reset (new `config` + stream). Capture/encode run only while ≥1 client is connected.
- **Controls are two configurable D-pad groups** (owner design): each group shows one category of up to 4 buttons, arranged as a D-pad cross in landscape and a column in portrait. A small dashed centre button opens a **tap-based** category wheel (tap to open, tap an item, ✕ cancels — no hold/drag). Default sets (owner 2026-08-04, see [ACTIONS.md](ACTIONS.md)): **Mouse** (Click/Right/Middle as CLICK/HOLD + Scroll; the side buttons Btn 4/Btn 5 wait in the pool — owner 2026-08-05), **Input** (Keys / Enter / Esc / Mic — Enter and Esc switch keyboard+mic OFF first; Mic = direct voice via the shell's `Android.startVoice()` SpeechRecognizer bridge (subsystem in `android/.../VoiceInput.kt`), results typed as `key_text`; only ONE of mic/keyboard is ever ON and a tap on the stream switches both OFF. **The dictation language is a USER CHOICE** (owner round 2, 2026-08-05 — round-1 evidence: pinning to the phone's FIRST system locale transcribed the owner's Serbian as English garbage, his phone lists English first; and the transient diagnostic toast was rejected angrily): the FIRST Mic tap opens the **dictation setup card** (plain language, persistent, Tailscale-card pattern — candidates = system locales + keyboard languages, LANGUAGE-AGNOSTIC, statuses "ready"/"model will download"/"online"), the choice is changeable any time via Settings → **Language** (the `dictation` action REPLACED `anywhere` in the default Settings set; `anywhere` stays in the action pool — ROADMAP preset combining), a missing-but-supported model auto-downloads while online recognition serves the SAME chosen language and the Mic button wears a dashed/pulsing look (`__voiceState`), the switch to on-device is SILENT when the model lands, and diagnostics go via `__voiceInfo` → `client_log` to the SERVER LOG — never a panel on the phone. Round 4 (owner 2026-08-05): the card also holds "More languages…" (downloadable models + the online service's list, collapsed behind one row) and "Mute listening beeps" (default ON — the round tones cycle on every silence); **the LOCK button stops EVERYTHING** — the shell's `onPause` cancels the listening round and refuses new ones until resume, the page switches mic+keyboard OFF on every hide (rounds used to keep beeping under a locked screen); and the server runs the Controls-editor's shipped-pools merge ONCE AT START (`web._merge_shipped_actions`, FROZEN-only) so default-set updates reach the phone without opening the editor), **Attach** (Gallery / Shot / Camera / Files — every source ends as a paste on the PC; gallery/Files multi-select, one image = bitmap, several or non-image = REAL files via CF_HDROP + `/upload_files`), **Edit** (All/Copy/Cut/Paste with icons) and **Settings** (Monitor switch moved here + next_input + quality + anywhere). Zones is NOT shipped — a custom-category story. **App-aware sets** (`app_sets` in actions.json) exist ONLY in layout focus: when the focused layout's process matches (VSCode/Chrome/Explorer shipped), the set appears as an extra wheel category and vanishes with the focus — nothing switches by itself. **Wheel composition** (owner 2026-08-05, revised same day): Mouse, Input and Settings are `required` — never hideable; every other shipped set (Edit, Attach, Navigate, Cursor, Media, Windows — the last two off by default) and every owner-made `custom_sets` entry (created ONLY in the desktop Controls editor — see [ACTIONS.md](ACTIONS.md)) toggles via the desktop default (`enabled`) + the phone's Settings → `sets` picker (per-device via the shell's `Android.prefGet/prefSet` SharedPreferences bridge — NOT bare localStorage, which is per-ORIGIN and silently split state between the LAN and Tailscale addresses, the "picker rotates" bug of 2026-08-05; localStorage stays only as dev-browser fallback); the app set rides along in layout focus without charging the count; hard cap 8 with non-required sets bumped from the end; any set may carry per-orientation button arrangement (`order_land`/`order_port`, shipped order = restorable default). **Every set carries a POOL, not four fixed buttons** (owner 2026-08-05): `buttons` may hold more commands than a D-pad shows — the RESERVES (VSCode Markdown preview `ctrl+shift+v` + next/prev tab, Chrome prev tab, Explorer tab hops, Edit Save/Undo/Redo, Windows snap/min/max, …) — and `active` names the four that ride, BY ID (`id | action | chord | key | label`, never an index, so a later version inserting a pool command cannot re-point the owner's choice; no `active` = the first four, so pre-pool files keep working). The commands of built-in and app sets are ours — the owner picks from the pool, he does not rewrite them; custom sets stay fully editable (owner decision 2026-08-05). Top-left **Layout (+)** (arms the next tap to pick a window for a new layout — the old Move/pan button is GONE, owner 2026-08-02) and top-right **Hide** (hide all controls) are fixed; top-center is the **layout bar** (big SVG ‹ › arrows OUTSIDE a framed app/tab name, plus ✕ to remove the focused layout) — it exists only while at least one layout does, cycles Desktop → layout 1 → … , and tapping the framed name opens the **layout list** (every layout at once, for when stepping one by one is too slow — owner 2026-08-03), where each row's ratio button opens that layout's **aspect-ratio panel** (W : H fields + preview, applied only on "Apply"). In layout focus the view is BOUND to the member window's region: **two fingers pinch-zoom and pan there exactly as on the desktop** (owner 2026-08-04 — no reason for zoom to be missing), with the region fitted to the screen as the maximum VISUAL zoom-out and the default on every layout switch — pinching out PAST the fitted view continues as the **font-zoom staircase** (owner 2026-08-05): each step sends Ctrl+`-` to the layout window so its own content shrinks (wide articles become fully visible), and pinching back in first undoes those steps with Ctrl+`=` before normal visual zoom resumes; layout focus ONLY, effect is whatever the focused app does with those chords (browsers/editors scale, some apps ignore it — accepted); the view and the cursor stay clamped inside the region ( phone rotation locked to the layout's orientation via the `Android.lockOrientation` bridge; full desktop = rotation free). Everything else — mouse modes, keyboard, monitor, snap, and chord shortcuts — is a category button defined in the owner-edited `actions.json` (see [ACTIONS.md](ACTIONS.md)), re-read every connection; the client renders from config and never hardcodes the layout. Custom-set editing UI and login belong to the future desktop GUI (owner decision).
- **Canvas modes are toggles; mouse BUTTONS are click/hold** (owner 2026-08-04, refining the 2026-07-26 rule): a single active `touchMode` — `move` (default: cursor only, never clicks) · `scroll` (· `drag`, unshipped — redundant) — decides what one finger ON THE CANVAS does; tapping a mode button toggles it; two fingers always pinch-zoom; nothing on the canvas is ever a tap-action. The **Click/Right/Middle buttons** however are real mouse buttons: tap = click, holding the finger ON THE BUTTON holds the PC button down (drag/select with the other hand steering) — `press {button, down}`; pointercancel always releases, so no PC button can stay stuck. Do not reintroduce tap-to-act on the canvas or a separate `hover` mode — cursor-only IS the default.
- **Keyboard capture is invisible** (owner decision 2026-07-22, reversing the visible top bar — the bar only mirrored what the PC screen already shows): the `<textarea>` stays `opacity:0`; typed/dictated text is watched in the focused box on the streamed PC screen itself. The IME's ↵ key and IME-committed `"\n"` both become **Shift+Enter** (new row — messengers keep typing instead of sending); the real Enter (activate/send) is the D-pad **Enter** button (`key_special enter`) in `actions.json`.
- **Phone → PC content** (the Attach set, owner 2026-08-04 — grew out of the single `upload` action): every source ends the same way — content in the **PC clipboard**, **Ctrl+V injected by the server** (picking was the whole gesture, owner 2026-07-22). ONE image → `/upload` → CF_DIB bitmap (pastes into any image box; Pillow-first decode with `pillow-heif` — phone cameras default to HEIC — EXIF-corrected, cv2 fallback). SEVERAL files or any non-image (PDF…) → `/upload_files` → temp drop folder + **CF_HDROP** (real files, like Copy in Explorer; the previous upload's temp files are cleared on the NEXT upload, not after paste — the target app may read the clipboard lazily). The shell's file chooser honors the page inputs: `multiple` (gallery/Files), `capture` (Camera → TakePicture via FileProvider; CAMERA runtime permission — the manifest already declares it for QR). Shot = PC screenshot of the viewed region (see the protocol above). `snap` (full monitor, clipboard only) is not in the default layout.
- **Updates flow downhill: GitHub → PC → phone** (owner request 2026-07-22). Only the DESKTOP app checks the internet: once per start it asks the public repo's latest GitHub release (`updates.py`, `update_repo` in config) and shows an in-window "Update to vX" button — download installer, launch, quit. The PHONE never checks the internet: `config.app_version` tells the page what the PC runs, the `Android.appVersion()` bridge tells it what the shell is, and a newer PC shows the "Update the app" banner → `Android.update()` downloads `/app.apk` from the SAME PC via the system browser. Publishing a GIT RELEASE (tag + `RemoteUser_Setup.exe` asset) is what lights the desktop path up.
- **Rendering is two layers** (owner request — smooth pan/zoom): a full-monitor **base** frame kept in memory (drawn always, so motion never flashes blank) plus the sharp **region** crop drawn on top when zoomed. Full native resolution is never streamed live (bandwidth); the base is the last full frame, the region refreshes while zoomed.
- Region streaming: when zoomed, the client requests its visible region (`viewport`); the server crops the 4K frame to it before downscaling — zoom stays sharp at constant bandwidth. Full frame = region (0, 0, 1, 1).

## Testing Notes

- Gesture disambiguation (tap vs drag vs scroll) can only be tuned on a **real touch device** — do not assume defaults are right.
- Test Unicode injection against real targets (VSCode, browser inputs) — VK_PACKET has known quirks in some apps (e.g. Windows Terminal surrogate-pair bugs).
- After long-running capture sessions, verify frame latency fresh — restart before measuring (see [Code Rules](../../rules/CODE.md) → Profiling).
