# Vibe Coder - decisions and architecture constraints

Every owner decree, ruling and live-defect finding this project is built
on, with its date. `CLAUDE.md` names only the laws a session must obey;
the reasoning, the reports behind them and the corrections made in place
live here. Wire-level detail is in [PROTOCOL.md](PROTOCOL.md).

## Product direction and stack (decided 2026-07-22)

**The authoritative record of the product direction and build plan is [ROADMAP.md](../ROADMAP.md#direction) (Product Direction, decided 2026-07-22). Read it before proposing architecture changes.** Summary:

- **Server:** Python 3.13, FastAPI + uvicorn, `dxcam` (DXGI capture), `ctypes` → Win32 `SendInput` (injection), `qrcode` (pairing). Two entry points around one `server_core`: `gui_main.py` (PySide6 window + tray — what the packaged EXE runs) and `main.py` (headless CLI). `bootstrap.init_process()` (DPI → logging → user settings) MUST run before any screen-touching import.

- **Streaming:** **H.264** via ffmpeg, hardware-encoded with auto-detection (NVENC → QuickSync → AMF) and a **libx264 software fallback** so it runs on any PC; output is fragmented MP4 decoded by the client via MSE, at **native monitor resolution** by default (`h264_max_width`). JPEG-per-frame is the fallback when no ffmpeg/encoder exists. (Measured ~3.6 Mbps static native 4K vs ~37 Mbps JPEG at quarter resolution.) Bundled ffmpeg is **pinned to 7.1.1** — newer builds require NVENC API 13.1 (driver ≥ 610) and silently drop to software encoding on older drivers.

- **Product = two installable apps:** a Windows desktop app (server + GUI + tray, `.exe`) and an Android **hybrid** app (native Kotlin shell in `android/` + WebView reusing the web client, shipped as an APK; the shell adds only what a browser cannot — pairing, real-app link routing, file chooser, `Android.rescan()` / `Android.setTailscaleUrl()` bridge — ALL guidance lives once, in the page). The shell stores **two addresses** (LAN from pairing + Tailscale learned from every `config` via the bridge) and probes `/ping` on both at start, loading whichever answers — the app connects at home AND on mobile data with no user choice (a single stored URL was the live failure: LAN address on mobile data = minutes of `ERR_CONNECTION_TIMED_OUT`). The probe counts ONLY the exact 204 as alive (captive portals on foreign Wi-Fi answer anything with a 2xx/redirect login page — live failure 2026-07-27; the 204 contract is pinned in the build gate), the error card keeps re-probing by itself (4 s timer + instant re-probe on every default-network change) because a one-shot "Try again" always fired mid-flap on flaky foreign Wi-Fi, that card names the CAUSE instead of one generic message (owner 2026-08-04 — no network / PC not on Tailscale / Tailscale missing / Tailscale off / PC down, read from network capabilities + package visibility, with the primary button being the fix: Install Tailscale, Turn Tailscale on — the shell opens the app since Android cannot flip another app's VPN switch — or Try again), and a session running over an unfamiliar Wi-Fi (LAN dead, tunnel alive, Wi-Fi transport) gets a one-per-stay security toast.

**NO browser EVER shows the client — on ANY device** (owner rule 2026-07-22, shouted; hardened 2026-08-02 after the live tablet failure: Chrome on Android tablets sends a desktop-Linux User-Agent with no `Android` token, so "detect Android" routing served the tablet the live client): the server serves the client ONLY to the APK's WebView (it appends a `VibeCoderApp` User-Agent marker) and routes every other User-Agent to `client/install.html` — a full-screen funnel whose FIRST, primary button is **Open the app** (`intent://pair?url=…` hands the tokened URL to the app; it pairs itself — nothing typed, nothing scanned; a camera-scanned QR always lands in the browser first, an Android platform limit for plain-http links, so every post-install scan must be exactly one tap), with the one-time Install (`/app.apk`) below it. After install the QR is not part of daily use — the user just opens the app; re-pairing happens IN the app. Desktop browsers get the funnel too (dev exception: only a checkout with no APK built serves the client — an official install always bundles the APK). The desktop installer bundles the APK.

- **Connection:** a mesh VPN installed on both devices (Tailscale recommended), one-time, wizard-guided; works anywhere incl. mobile data via the mesh's free relay. Server already binds all interfaces + pairing detects the Tailscale address, so this is code-ready.

- **Login = the Tailscale login** (owner decision, option a): the mesh identity IS the account; one login per device, no custom account backend.

- **The app installs/drives all dependencies — the user never side-installs anything** (hard owner requirement). Wizard in the `.exe` AND the APK: ffmpeg bundled; Tailscale chain-installed on desktop / store-deep-linked-and-detected on Android; user only follows in-app prompts. Never tell the *end user* to download/copy/configure anything (telling the *owner* to install a dep for dev-time testing is fine, but say so explicitly).

- **Client UI:** vanilla HTML/CSS/JS in the WebView, Pointer Events, canvas rendering — no framework, no build step.

- **Hard constraints (owner):** no payment for any required part; third-party services/installs OK if best; not over-indexing on privacy/security. Don't fight mature remote-desktop tools on latency — the unique value is the **app-aware companion layer** (Windows UI Automation state reading, notifications, per-app controls).

- **Open decisions** (see ROADMAP): mesh provider (Tailscale vs ZeroTier), distribution (APK vs later Play Store), build order.

## Build and release (owner verdict 2026-08-18 replaces the old order)

The desktop installer is `setup/build.py` (it bundles the client and the
freshly built APK); the APK alone is `setup/build_apk.py`, built first when
`android/` or `client/` changed. **Neither is ever run without the owner's
word in that session** - the root constitution's Law 4. What still holds
from 2026-07-22 is the reason releases matter here: the owner tests and
updates ONLY through the official GitHub release, never the dev server from
VS Code and never the local `dist/` - an unreleased fix is a fix he cannot
see, which is why a session that changed server, client or android code
ends with `## BUILD & RELEASE?` and the exact command.

## Guidance lives in the apps, never in chat or manuals

- **Everything is guided IN the apps — never in chat/manuals** (hard owner principle, restated angrily 2026-07-22 and binding): any step a user must perform gets step-by-step on-screen guidance with plain language and automatic continuation. Desktop: three-state Tailscale card (install / sign in / connected). Phone first contact: the **QR always encodes the LAN address**, and the FIRST scan hard-requires the phone on the home Wi-Fi (a fresh phone has no tunnel to the PC — with mobile data the LAN address loads NOTHING, just a dead dark page; hit live 2026-07-22). The PC window states this requirement under the QR — the only place that can, since an unreachable page cannot guide anyone. Opening the QR in the phone browser lands on the **install funnel** (Open the app first/primary; Install below → paired automatically via `intent://` — the browser never shows anything else). Inside the app, the client page shows an "anywhere access" banner (auto-appears ONCE per device — owner 2026-07-26; afterwards Settings → Anywhere reopens it) → in-page wizard: Google Play deep link for the Tailscale app → sign-in step → the page polls `GET /ping` (auth-free 204, reachability only) on the Tailscale address and hands over the permanent works-anywhere link the moment the phone joins. Never send the end user outside the guided flow.

## Architecture constraints

### 1. One monitor per view.

**One monitor per view.** The client always displays and controls exactly one monitor; a switch button changes which. Client coordinates are ALWAYS normalized 0–1 within the displayed monitor; the server maps them to that monitor's rect. Never send virtual-desktop-wide coordinates.

### 2. The server process must declare DPI awareness

**The server process must declare DPI awareness** (`DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2`) before any capture or injection — otherwise Windows silently rescales injected coordinates.

### 3. No input before auth.

**No input before auth.** The WebSocket handler rejects every message until a valid token arrives. This is a hard security rule (Remote Mouse CVE class), not a nice-to-have.

### 4. Unicode text goes through `KEYEVENTF_UNICODE`

**Unicode text goes through `KEYEVENTF_UNICODE`** (VK_PACKET), never through virtual-key mapping. Special keys (Enter, Backspace, arrows, Tab, Esc) go through VK codes. Two distinct protocol messages: `key_text` vs `key_special`.

### 5. Client keyboard capture:

**Client keyboard capture:** an invisible but REAL-SIZE focusable `<textarea>` — full-width, ~42px tall, at the top, rendered fully transparent (transparent text/caret/background) with `pointer-events:none`, font ≥16px. NOT `display:none`, NOT `opacity:0`, and NOT 1px×1px: a 1px field made Android IMEs silently refuse to raise the keyboard / attach voice input (found live 2026-07-22 — typing and dictation both dead). A textarea so the phone IME shows ↵/new-row instead of a Send/Go key; `autocapitalize/autocorrect/autocomplete/spellcheck` disabled; printable characters via input-event diffing (the diff replays surviving-suffix edits too), structural keys via `keydown`. Never trust `keydown.key` for printable characters (Android IME).

### 6. The finger steers, buttons act — and NOTHING is a tap

**The finger steers, buttons act — and NOTHING is a tap** (owner decision 2026-07-22, hardened 2026-07-26): the one-finger gesture ONLY moves the PC cursor — it never clicks. Left AND right clicks are explicit press buttons (`click {button}` — down+up at the current cursor position; twice fast = double click); the old right-click-on-tap mode is GONE — with the offset pointer a tap would land away from the fingertip, so no canvas tap may ever act. Toggle modes (drag/scroll) stay; two fingers = local pinch zoom/pan, never clicks. No timed gestures, ever.

**The pointer sits EXACTLY under the finger** (owner decision 2026-08-02, reversing the 2026-07-26 offset system after living with it on-device): no handedness diagonal, no calibration, no reserved edge margins — the image aspect-fits the FULL canvas and a focused layout touches all four screen edges. `config.hand` is GONE (owner decree 2026-08-07: *"briši sve vezano za to levu desnu ruku ... i sve ono što smo računali offset ... ne držimo legacy stvari već ih uklanjamo"*) — the server no longer sends it, there is nothing left to ignore, and the `calibrate` action, its icon and every doc page still describing the handedness diagonal, the calibration samples and the reserved edge margins went with it the same day. Those pages were the real danger: the code had been dead since 2026-08-02 while the documentation still explained it as live, naming functions that no longer exist. The design going forward is gamepad-first, not finger-handedness.

### 7. Ghost-pointer self-healing

**Ghost-pointer self-healing** (live bug 2026-07-22): Android WebView occasionally loses a `pointerup`/`pointercancel`; a stale entry in the pointer map made EVERY later tap register as a pinch until page refresh ("input randomly stops working"). On every `pointerdown` with `isPrimary`, the client wipes pointer/pinch/primary state — a new primary pointer is the browser's guarantee no other finger is really down. Do not remove this reset.

### 8. Session lives only while the owner is looking

**Session lives only while the owner is looking** (owner security decision): the client closes the WebSocket when the page is hidden (tab backgrounded / screen locked) and reconnects **immediately** on return (`visibilitychange` → connect, not just the 2 s retry interval — the wait swallowed the first taps after every app switch). A `send()` on a dead socket must stay VISIBLE (status pill "Reconnecting…") — silently dropping it read as "buttons randomly stopped working" over a frozen frame.

**UIPI is the proven total-input killer and is now DEFENDED twice** (live failure 2026-07-29, the recurring "every release breaks the mouse" ghost): Windows silently discards ALL `SendInput` from a non-elevated process — the call still returns success — whenever an ELEVATED window has focus (the owner's admin VSCode after every dev session; stream fine, zero errors, dead mouse; confirmed by controlled A/B on the installed app — medium = zero movement, elevated = pixel-exact). Defense: (1) the packaged app runs **elevated always** (`--uac-admin`; autostart via Task Scheduler `/RL HIGHEST` because HKCU Run silently skips elevated apps); (2) the injector **verifies its own moves** (`InjectionMonitor`: commanded jump ≥ threshold must land; a miss streak → server ERROR log + client toast) — if anything ever eats input again (lock screen, future policies), the phone SAYS so instead of gliding a local cursor over a dead session. The monitor's logic is pinned in the build gate; never remove either defense.

### 9. Control buttons fire on pointerup PLUS a pointercancel rescue, and the input pipeline is gated

**Control buttons fire on pointerup PLUS a pointercancel rescue, and the input pipeline is gated** (live failure 2026-07-26 — every button dead on the real device, only the keyboard toggle alive): Android ends touches that start near screen edges / system-gesture zones with a `pointercancel`, so an up-only tap handler simply never runs — and with `targetSdk 35` the WebView is drawn edge-to-edge, so the nav bar also sat ON TOP of the bottom controls (the shell now hides the system bars — immersive, swipe reveals them transiently). `keepFocus` therefore fires on pointerup (touch grants transient user activation at UP — the file picker and IME focus need it; plain down-firing broke them) AND on a pointercancel whose travel stayed under `CANCEL_TAP_SLOP` — a stolen tap still acts, while a system home/back swipe crossing a button (real travel, then cancel) never does. Never simplify this back to bare `click`/pointerup, and never remove `tests/test_input_pipeline.py` from `build.py` (the fail-closed INPUT GATE that proves touch → protocol → injection end-to-end before anything ships; its layout comes from `tests/fixtures/actions.json`, pinned so owner edits to the real actions.json can't block builds).

### 10. Nothing we raise may outlive us in the always-on-top band

**Nothing we raise may outlive us in the always-on-top band** (owner decree 2026-08-05, after his own Chrome and VSCode were left nailed above everything twice). Every window the phone raises is written into a LEDGER (`window_manager.mark_topmost`), and there are exactly two ways out, one per way the process can end: (a) we get to run code — tray Quit, server stop, Apply & restart, Ctrl+C, a console close, an unhandled crash, logoff — and `release_all()` walks the ledger, wired into `ServerController.release_windows()`, Qt `aboutToQuit`, `atexit` and a `SetConsoleCtrlHandler`, all idempotent; (b) we do NOT — Task Manager, the installer's `taskkill`, a power cut — so the ledger is mirrored to `%LOCALAPPDATA%/VibeCoder/topmost.json` on every change and `repair_stranded()` fixes it at the next start, touching a window ONLY while it still runs the executable it ran when we raised it (a recycled handle must never cost a stranger's window its z-order). `raise_window(hwnd, topmost=False)` exists for the transient raises that are NOT layout membership (tab extraction, `next_input`) — those windows belong to no layout, so a topmost raise there stranded them for the rest of the Windows session. `prune()` drops only CLOSED windows, never merely cloaked ones: Windows cloaks every window on another VIRTUAL DESKTOP, so pruning on visibility deleted the owner's layout the moment he pressed Win+Ctrl+Right and abandoned its members up there.

### 11. What the phone types lands where the owner is LOOKING

**What the phone types lands where the owner is LOOKING** (owner report 2026-08-06, three times in one evening — and the fourth report was the bug itself: a sentence he dictated for another project arrived in this project's session). `SendInput` has no target: every dictated character goes to whatever window Windows calls the FOREGROUND at that instant, so anything on the PC that takes focus mid-sentence — an app starting, a dialog, another agent's editor window — takes the rest of the sentence with it, silently, while the stream still shows the PC. `server/focus_guard.py` decides the target BEFORE every message that types (`key_text`, `key_special`, `chord`, `paste_text`, `screenshot`): **in a layout the fence is the layout** — a foreground outside its members is refused, focus goes back to the member the phone was last typing into, and only then do the keys go out; **at the full desktop** the target is the window the typing burst started in, re-armed only by what the owner does on purpose (an injected click, `next_input`, a layout/monitor switch — a thief sends no message and arms nothing); **a dialog of the target is the target** (owner chain, never process identity — every VSCode window shares one process and one of them is exactly the thief); and **the thief is NAMED in the log** every time, because the app being the last to know is what cost three reports. The other half of the same bug lives in `Layout.last_member`: `focus()` raises the keyboard member LAST, since one excursion (picker, permission dialog) closes the socket, the page re-focuses the layout, and raising members in list order handed the keyboard to whichever window sat last in the grid. Gate: `tests/test_focus_guard.py`, fail-closed in `build.py` (0e/6) — never remove either half.

**And a focused layout is DEFENDED, not merely checked** (owner decree the same evening, shouting — "kada uhvatimo fokus lejauta ne može nikakav program da izbaci fokus"): `focus_guard.watch` is one task per connection that polls the foreground every 0.25 s and puts it straight back inside the layout, because Android's recognizer delivers a whole utterance only at the END of a round — a program that steals focus mid-sentence does not misplace a character, it takes the window half an hour of speech was meant for. The watcher sleeps while the phone is away (those windows belong to the desk again) and never defends the DESKTOP pin (no fence there — fighting the whole desktop would be us stealing focus). The phone's half of the same failure: `EXTRA_PARTIAL_RESULTS` is on and `VoiceInput.partial` is a rescue copy — a round that dies without a final result (`ERROR_CLIENT`, a network drop) types what it already heard instead of deleting it, and `deliver()` is the only exit so nothing is typed twice.

### 12. A gamepad press IS a button press

**A gamepad press IS a button press** (build rounds R6/R7, owner spec 2026-08-07). The controller pairs with the PHONE and the WebView does not reliably expose the Gamepad API, so the Android shell captures every `KeyEvent`/`MotionEvent` (`android/.../Gamepad.kt`, claimed at `dispatchKeyEvent` before the WebView's own D-pad focus handling can fight it) and hands them to the page as `__padButton` / `__padAxis` / `__padInfo` — the shell adds only what a browser cannot.

**The MAPPING lives on the page** (`client/gamepad.js`) on the existing protocol: the server needs nothing new, and a mapping change ships with the PC's page instead of a new APK. Every mapped button goes through **`buttonPress()` in controls.js — the same activator object a finger's `pointerup` runs** — so CLICK/HOLD (`press {button, down}`), the pointercancel rescue and `keepFocus` can never have a second copy to drift from; constraint 9 is why. D-pad = the LEFT group's four buttons BY SLOT (so it survives `order_land`/`order_port`) and holding holds the PC button; △◻○✕ = the RIGHT group's; L2/R2 = Layout (+)/Hide; L1/R1 **held** opens that side's category wheel and a stick POINTS at the set (release confirms, releasing at nothing changes nothing), while a short TAP steps the layout bar; left stick steers on a deadzone-plus-power curve (0.15 deadzone clears stick drift, exponent 2 so half tilt is a quarter speed — linear is unusable for precision on 4K); right stick scrolls, vertically and horizontally (`hticks`); L3/R3 = double-click / middle click; Start/Select = Keys / the layout list. A pad press also re-arms the screen-awake timer — it is neither a touch nor a keydown, and without that a controller-only session went dark and the PC correctly packed the layout away mid-work. Gate: the pad block in `tests/test_input_pipeline.py`, fail-closed in `build.py`; it pins the curve's SHAPE, never its numbers, because the owner tunes those on the real controller.

### 13. A layout's arrangement is MEASURED, never remembered

**A layout's arrangement is MEASURED, never remembered** (owner report 2026-08-07, the third round of the Move handle). `Layout.arranged_ratio`/`arranged_pos` were a note of what was COMMANDED, written before `place_window` was even called — so the moment a member left its rect (the app re-laying itself out, a restore out of the taskbar, a Windows snap, a placement that quietly did not take), the note became a lie and every later Apply of the SAME position matched it and re-placed NOTHING: the phone's panel moved and the PC never did again ("uvek ostavi centrirano"), which is why retrying never helped him. `LayoutRegistry.focus` now computes the targets fresh every time, asks `_standing()` where the windows REALLY are (`grids.at_rect`, ±8 px — the same tolerance `wait_landed` uses, so a min-size app that legitimately sits larger is not re-placed forever), and writes the note only when the placement LANDED; a refusal is logged by name, toasted to the phone and retried on the next focus. Gate: the placement-RECT checks in `tests/test_layout_protocol.py`, fail-closed in `build.py` (0f/6). The process lesson is mechanical: two rounds closed this while it was broken because one measured a pure function's return value and the other measured a JS variable, and the gate's own fake `place_window` threw the commanded rect away — a check on a value the user cannot see proves nothing about a feature he judges by geometry. Round FOUR closed the other half of the same lesson (owner decree 2026-08-09): even a MEASURED, landed placement was the wrong SCREEN — the server crops the region and streams the same picture wherever the windows sit inside the monitor, so moving them by `pos` changed nothing on his tablet. `pos` now anchors the letterboxed picture ON THE PHONE (`client/view-anchor.js`; gate `tests/test_view_anchor.py` computes the geometry HE judges), the server always centers the windows, and `arranged_pos` is gone — placement depends on `arranged_ratio` + `place_pending` + `_standing`, and a pos-only Apply re-places nothing while its `layout_state` still carries the anchor to the phone.

### 14. The dictation types WHILE he speaks, and only what has SETTLED

**The dictation types WHILE he speaks, and only what has SETTLED** (owner decree 2026-08-08: *"ne dopuštamo da on čeka dok ja stanem sa govorom, već da namjerno izvlačimo iz njega tekst"*, and the reason — *"mogu da pričam 10 minuta bez prestanka a onda ne upiše ni 1 reč... usred toga dođe do prekida... nestane sve što sam do sada pričao"*). An Android recognition round lasts as long as he keeps talking, so the rescue copy of constraint 11 only ever saved a round that DIED — a round still alive held ten minutes of speech hostage, and locking the phone or taking a call discarded all of it. Every partial is now forwarded to the page (`VoiceInput.onPartialResults` → `stream()` → `__voicePartial`), but **nothing may simply be typed as it arrives**: a recognizer REVISES its guess ("je" becomes "jeste" two words later) and we type into a FOREIGN application through `SendInput` — no composing region, no undo, **no way to unsend a word**, which is exactly what Google's own keyboard can do inside its own field and we cannot do inside his. So a word goes out only once it is **outside the held tail AND unchanged since the previous partial** (`client/voice.js` — `VOICE_HOLD_WORDS` is 3: the engine rescores the phrase it is still forming, so revisions land in the last one to three words, and three is also the length of the re-heard boundary fragments of the round-boundary trim below, so a shorter hold would let a duplicate out before the overlap can be seen). What that buys is his actual requirement: an interruption costs **the held tail, ~1.2 s of speech, never the monologue** — everything before it is already on the PC, and the round's end (final, or the rescue of a round that died) flushes the rest with what streaming already sent trimmed off the front. A final that CORRECTS an already-typed word is DROPPED, not applied: blind backspaces would eat whatever the PC caret is really sitting in. `onBackground()` still cancels everything and clears all state (the LOCK rule) and deliberately does NOT flush — the page has already closed the socket by then, so a flush would record the words as sent and lose them for good. The rules live on the PAGE, in a module kept PURE so the gate runs it whole: `tests/test_voice_dedup.py`, fail-closed in `build.py`, driving realistic partial SEQUENCES with a revision planted mid-stream — a rule about revisions cannot be proven by one call, and this repo has no JVM test runner, which is how the same feature shipped half-done before.

### 15. We never estimate how long another program needs — we watch for the condition

**We never estimate how long another program needs — we watch for the condition** (owner ruling 2026-08-12, after asking exactly the right prior question: *"odluka zavisi od 1 faktora a to je da li stvarno nemamo nikakav respons ... što čisto sumnjam"* — lang-ok: owner quote). His ruling is general and not about one file: *"mi da procjenjujemo koliko nečemu treba da se učita je nešto što nije dozvoljeno ni na tom ni na bilo kojem drugom mjestu"* (lang-ok: owner quote). A fixed sleep placed where another application's UI is expected to have caught up is a guess that is wrong in both directions at once — too long on his fast PC (dead time he watches) and too short on a slow app (a failure he then reads as a wrong layout, because tab extraction falls back to the whole window). Every such sleep in `server/uia.py` is now a `_poll()` on the observable condition — the context menu really holding its item, the Explorer address band reading an existing path stable across two reads, the raised window really being the foreground one, the tab count really dropping, the torn-off window really existing and its rect really standing still — and the old number survives ONLY as the give-up point. Where a timeout is reached the code refuses rather than proceeds on hope: the `Ctrl+W` that closes the extracted tab is SKIPPED and logged if the source window never took the foreground, because closing a tab in a stranger's window is far worse than leaving one open. The one exemption is named in place so nobody "fixes" it: the 8–40 ms micro-sleeps inside `_click`/`_held_drag` are the physical pacing of an injected gesture — a real held-button drag needs real milliseconds between its own synthetic input events to register as a drag at all — and they are not an estimate of anything.

### 16. There are two loading animations, and which one is used depends on what is happening BEHIND it

**There are two loading animations, and which one is used depends on what is happening BEHIND it** (owner decree 2026-08-12, and he named both: *"1. vrsta je loading full screen / 2. vrsta je loading samo CUBE bez background"* — lang-ok: owner quote). `LOADING_FULL` is the opaque veil and is used where the PC's own picture is about to change in a way he must not watch — windows climbing out of the taskbar, a grid being built, a layout torn apart. `LOADING_CUBE` drops the veil, shrinks the cube to a badge and puts the label in a bordered pill of its own, and is used where we are only WAITING FOR AN ANSWER or watching something open that is worth seeing open; his own example is Chrome, *"na taj način će korisnik znati da se dešava učitavanje ali će i vidjeti da se u pozadini otvara"* (lang-ok: owner quote) — there is nothing ugly to cover there, only time to account for, and covering it would hide the only progress there is.

**Both are the FRONT and gate nothing behind them** (*"loading animacija je uvek FRONT i nikada ne treba da zavisi od nje ono što se dešava iza"* — lang-ok: owner quote): no server path waits on the overlay. Both still block taps — bare is transparent, not inert. Every call site passes its kind explicitly AND carries a matching `// LOADING: FULL|CUBE — why` comment; the gate `tests/test_loading_kind.py` (fail-closed in `build.py`) holds the two to each other, because a stale inventory comment is worse than no inventory, and that inventory is what the eventual move to the shared **Loading Cube** gadget will be read off. The overlay had never been PHOTOGRAPHED in this project's life until this round — staging it in the phone audit immediately found two defects in the shape that had shipped all along (the label sitting on the cube, because a rotated 110 px cube overflows its own box by ~22 px and ate the gap; and a truncation tooth that had never met a PROGRESS ellipsis, now declared with `data-in-progress` rather than quietly exempted).

### 17. There is ALWAYS a way back to a window, and finding it is GEOMETRY — never history

**There is ALWAYS a way back to a window, and finding it is GEOMETRY — never history** (owner report 2026-08-12, his FIFTH on one failure, and he named its class: a game-breaking bug). A window that opened while his phone was LOCKED — an agent's HTML report — stands off every screen and can never be shown again: a phone has no taskbar, and until this round nothing in this codebase could move a window it had not itself placed.

**The reason four earlier rounds could not even SEE it is the lesson, and it is bigger than the bug:** every rule in `server/layout_popup.py` stands on `baseline(conn)`, which files every window already standing when the phone connects as KNOWN — so a window born while nothing was connected is filed as old by the very connection that comes looking for it, and a feature whose trigger is a connection can never answer for what happened while there was none. `server/lost_windows.py` therefore asks the only question that needs no history — **can he reach it** — and asks it of geometry measured now: a window is reachable when a grabbable piece of its TITLE BAR (`GRAB_WIDTH_PX` x `TITLE_HEIGHT_PX`) lies inside some monitor's work area, never when some pixels of it happen to be visible (a body on screen under a caption above the top edge is exactly as lost), and a MINIMIZED window is judged by where it would RESTORE to (`rcNormalPosition`) — his report window went down with the layout that owned it, so anything that skipped minimized windows would have found nothing wrong. It sweeps at the DESKTOP as well as in a layout (a lost window is lost either way), offers the same chip the module next door already owns (`act:"rescue"`), and moves nothing until he taps.
